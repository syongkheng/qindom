## Open questions for the user (collected during autonomous run)

Design/security decisions the refactor deliberately left unchanged. To be decided together at the end.

**budget**

- B1. `POST /budget/:id/collaborator` tells any table owner whether an email has an account (404 vs 200): email enumeration, only global rate limits.
- B2. Invitees don't need a verified email (`email_verified` not checked).
- B3. Every collaborator sees the other collaborators' emails in `GET /budget/:id`.
- B4. Collaborators whose user account is soft-deleted still appear and keep their collaborator row.
- B5. Collaborators can't leave a shared table themselves (only the owner can remove them).

**siri-shortcut** (consumer = your iPhone Shortcuts; contract frozen)

- S1. V1 tap accepts blank `merchant`/`name` (stored `""`) and blank `amount` (stored as 0). Reject as 400, or keep lenient so a tap is never dropped?
- S2. V1 rejects amounts with thousands separators (`"$1,234.50"` → 400), so taps ≥ 1,000 may never be recorded depending on Shortcut formatting. Strip commas?
- S3. V1 accepts negative amounts. Keep?
- S4. (kept) `smsBody` now capped at 2000 chars (real alerts ~250; 10-part SMS ~1,530).

**hdb**

- H1. fndom `src/hooks/usePphsManager.ts` has no importer. The agent's delete was blocked by the permission system, so it was updated instead. Delete it?
- H2. ManagePphsDialog lets you edit town / siteExpiry / flatTypes, but the API only saves lat/lng (address-keyed), so those edits are silently lost.
- H3. `tb_hdb_pphs_coordinate` has no `source` column, so a manually picked point reads back as `"database"`. Add a column (migration) to record "manual"?

**wedding**

- W1. The confirmation email has no PIN (removed in 70d6778 with "Forgot PIN"). A guest who closes the success screen can't use the status lookup. Put the PIN back in the submitter's email?
- W2. jessikheng `src/utils/rsvpApi.js` still exports the dead `RSVP_RECOVER_PIN_ENDPOINT` (route no longer exists). Delete it there?
- W3. Submit isn't atomic (soft-deletes, then insert; concurrent same-PIN → 500). Revisit when utils adds logged transactions, or accept at wedding scale?

**itinerary**

- I1. `tgShortCode` ownership: `tb_tg_image` has no uploader column. Options: migration adding `created_by_id` on upload (true ownership), or the no-migration bind check `short_code = tgShortCode AND uuid = file.uuid`. Low gain (`/img/:code` is public anyway). Which, if any?
- I2. Blank fields never clear on update (blank → unchanged). Visible bug: moving an agenda item back to "unscheduled" doesn't persist; the same applies to clearing desc/category/budget/times/destination/remarks. Change to "blank → NULL"? (Risky if any client sends blanks for fields it didn't edit.)
- I3. Public views (`/v/`, `/challenge`) return the internal `id` and the owner's `sessionId`. Not exploitable, but unnecessary. Drop them (contract change)?
- I4. (note) fndom BookingDrawer `remarks` input has no `maxlength`, but the column is VARCHAR(128); >128 now gives a 400 toast. Add `maxlength`?

**auth** (security semantics deliberately unchanged)

- A1. `POST /auth/password/validate` lets a session holder guess the password with only the global 100/min limit. Add a limiter / attempt cap?
- A3. Admin role updates: an OWNER can remove their own SYSTEM_R5 (lock-out); `updateUserRoles` filters by `{id}` only (can edit deleted users) and returns `{updated:true}` for a nonexistent id. Return 404 / block self-demotion?
- A4. `issueSession` writes the token by `username_system` without `record_status`, so soft-deleted rows with the same `username_system` get it too (not observable today). Switch to `{id}`?
- A5. OTP uses `randomBytes(4) % 1e6` (tiny modulo bias). Switch to `crypto.randomInt`?
- A6. The password-changed email shows time in the server's timezone, not `APP_TIMEZONE`. Switch?
- A7. No max password length (bcrypt ignores bytes > 72); no caps on email/system (no CREATE migration for `tb_aa_user`, so widths unknown; an oversized email → 500 `registration_failed`). Add caps (need the column widths)?
- A8. PM2 logs contain plain emails (unverified login, max attempts, registration failed, password-mail failure). Mask them?
- A9. `/preflight` reveals whether an email has an account (by design) with only the global limiter. Add a limiter?
